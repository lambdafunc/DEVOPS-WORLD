## From Source Code to a Running Application Container

In Part 5, you learned how to create Docker images with Dockerfiles.


But knowing Dockerfile instructions individually is not enough.


# 2. What Does “Containerizing an Application” Mean?

Containerizing an application means creating a reproducible container image containing the application and the runtime components it needs so that containers can be created consistently from that image.

For example, a Python application may require:

```text
Python runtime
Python packages
Application source code
Configuration
Startup command
```

A Node.js application may require:

```text
Node.js runtime
npm dependencies
Application source code
Configuration
Startup command
```

A static website may require:

```text
HTML
CSS
JavaScript
Web server
Web-server configuration
```

Docker allows us to package these requirements into controlled images.

# 5. Preparing an Application for Containerization

Applications designed for containers usually work best when they follow several principles.

A container-friendly application should ideally:

```text
Start predictably
Run in the foreground
Read configuration externally
Write application logs to stdout/stderr
Handle termination signals
Expose a meaningful health endpoint
Avoid depending on local machine state
Avoid storing important persistent data only inside its writable layer
Run without unnecessary privileges
```

Think:

```text
Predictable startup
+
External configuration
+
Observable behavior
+
Clean shutdown
+
Minimal privileges
+
Replaceable container
```

# 6. Avoid Depending on the Developer's Machine

Suppose your application works because your laptop already contains:

```text
Python 3.12
Flask
curl
A configuration file
A local environment variable
A database client
A manually created directory
```

You create an image without accounting for these dependencies.

The application may fail.

Why?

Because:

```text
Host environment
≠
Container environment
```

The container only has what its image and runtime configuration provide.

# 7. Application Dependencies

An application dependency is something the application requires to function.

For a Python application:

```text
Flask
requests
gunicorn
psycopg
```

could be application dependencies.

For Node.js:

```text
express
pg
axios
```

could be dependencies.

These are usually described in dependency files.

Python examples:

```text
requirements.txt
pyproject.toml
```

Node.js:

```text
package.json
package-lock.json
```

The exact system depends on the project.

---

# 8. Runtime Dependencies

Application dependencies and runtime dependencies are related but not identical.

Suppose a Python application imports Flask.

Flask is an application dependency.

But Flask itself requires Python to execute.

Python is part of the runtime.

You might also need operating-system libraries.

Architecture:

```text
Linux Userspace
      ↓
Language Runtime
      ↓
Application Dependencies
      ↓
Application Source
```

For example:

```text
Linux
  ↓
Python 3.12
  ↓
Flask
  ↓
VERIQTA API
```

---

# 9. Build Dependencies vs Runtime Dependencies

Some dependencies are required only while building software.

For example:

```text
Compiler
Header files
Build tools
Development libraries
```

The application may not need them after the final artifact is produced.

This creates two categories:

```text
Build dependencies
→ needed to construct application/artifact

Runtime dependencies
→ needed when application actually runs
```

Why does this distinction matter?

Because putting unnecessary build tools into a production image can increase:

```text
Image size
Attack surface
Package count
Maintenance burden
Vulnerability exposure
```

Later, in Part 11, multi-stage builds will help separate these environments.

# 12. Full vs Slim vs Alpine-Style Images

You may encounter image variants such as:

```text
python:<version>
python:<version>-slim
python:<version>-alpine
```

They are not simply:

```text
Bad
Good
Best
```

They represent trade-offs.

A fuller image may provide more libraries and easier compatibility but be larger.

A slim image removes many unnecessary packages while retaining a familiar Linux userspace.

Alpine-based images can be very small, but Alpine uses musl libc rather than glibc, which can affect compatibility with some applications and binary dependencies.

Therefore:

> Smaller does not automatically mean better.

Choose based on application requirements.

# 13. Application Ports

Web applications usually listen on a network port.

For example:

```text
Python API → 5000
Node API   → 3000
Nginx      → 80
```

Inside the container:

```text
Application
    ↓
Container Port
```

But a container port is not automatically reachable from your host.

You may need:

```bash
docker run -p 8080:5000 image
```

Architecture:

```text
Browser
   ↓
localhost:8080
   ↓
Host Port 8080
   ↓
Docker Port Publishing
   ↓
Container Port 5000
   ↓
Application
```

---

# 14. The Application Must Listen on the Correct Interface

A common mistake is binding the application to:

```text
127.0.0.1
```

inside the container.

`127.0.0.1` is the container's loopback interface.

Instead, containerized web applications commonly listen on:

```text
0.0.0.0
```

which means:

> Listen on all available IPv4 interfaces in this network namespace.

For example:

```python
app.run(host="0.0.0.0", port=5000)
```

or Node.js:

```javascript
app.listen(PORT, "0.0.0.0");
```

---

# 15. `EXPOSE` Is Not Port Publishing

Dockerfile:

```dockerfile
EXPOSE 5000
```

documents:

```text
This application expects to use container port 5000.
```

Runtime:

```bash
docker run -p 8080:5000 image
```

actually publishes the port.

Remember:

```text
EXPOSE
→ image metadata/documentation

-p
→ runtime host-to-container port publishing
```

# 16. Environment Configuration

Applications should not require a different image for every simple configuration change.

Bad pattern:

```text
myapp-development
myapp-staging
myapp-production
```

where the application code is identical but simple environment settings are hardcoded differently.

A stronger pattern is often:

```text
One versioned application image
        ↓
Different runtime configuration
```

For example:

```text
APP_ENV=development
APP_ENV=staging
APP_ENV=production
```

# 20. Why Not Log Only to a File Inside the Container?

Suppose your application writes only to:

```text
/app/logs/application.log
```

inside the container writable layer.

Problems include:

```text
Container replacement may remove the file
docker logs cannot automatically show those application file logs
Log collection becomes more complicated
Local disk can fill
Multiple container replicas create fragmented logs
```

Production systems may use dedicated logging agents and platforms, but stdout/stderr is a strong container default.

# 22. Running Applications as Non-Root

A container does not become harmless simply because it is a container.

If the application does not need root privileges, run it as a dedicated non-root user.

Principle:

```text
Least privilege
```

Architecture:

```text
Container
   ↓
Dedicated Application User
   ↓
Only Required Permissions
```

This reduces the potential impact of application compromise.

---

# 23. Non-Root Requires Permission Planning

Do not simply add:

```dockerfile

```

and assume everything will work.

The application may need access to:

```text
Source files
Configuration
Temporary directories
Cache directories
Uploaded files
Runtime sockets
Application directories
```

You must ensure the runtime user has appropriate permissions.

# 26. Graceful Shutdown

Containers are expected to stop.

They may stop because of:

```text
Deployment
Scaling
Host maintenance
Application update
Manual operation
Failure recovery
Orchestrator action
```

A well-behaved application should shut down cleanly.

This is called graceful shutdown.

---

# 27. What Does Graceful Shutdown Mean?

Instead of immediately disappearing while processing work, an application may need to:

```text
Stop accepting new work
Finish or terminate active work safely
Close network connections
Close database connections
Flush important buffers
Release resources
Exit cleanly
```

Conceptually:

```text
Termination Requested
        ↓
Application Receives Signal
        ↓
Stop Accepting New Work
        ↓
Finish/Clean Existing Work
        ↓
Close Resources
        ↓
Exit
```

---

# 28. Signals

Linux processes receive signals.

Signals are notifications delivered to processes.

Important examples include:

```text
SIGTERM
SIGKILL
SIGINT
SIGHUP
```

You do not need to memorize every Linux signal yet.

For Docker, two are especially important:

```text
SIGTERM
SIGKILL
```

---

# 29. `docker stop`

When you run:

```bash
docker stop mycontainer
```

Docker does not normally begin by immediately killing the process.

Conceptually:

```text
docker stop
     ↓
Send configured stop signal
     ↓
Usually SIGTERM
     ↓
Wait for stop timeout
     ↓
Still running?
     ↓
SIGKILL
```

The exact timeout can be configured and platform/runtime details matter, but this is the essential model.

---

# 30. SIGTERM

`SIGTERM` means roughly:

> Please terminate.

The application can handle it and perform cleanup.

This enables graceful shutdown.

---

# 31. SIGKILL

`SIGKILL` is different.

The process cannot catch or ignore it.

The operating system terminates the process.

Conceptually:

```text
SIGTERM
→ opportunity to shut down

SIGKILL
→ forced termination
```

You generally want applications to exit cleanly before forced termination becomes necessary.

---

# 32. PID 1

Every Linux process has a process ID.

The first process in a process namespace has:

```text
PID 1
```

Inside a container, the main process normally becomes PID 1 in the container's PID namespace.

Example:

```text
Container
└── PID 1: application
```

This process is especially important.

---

# 33. Why PID 1 Matters

PID 1 has special behavior in Linux.

For containerized applications, it matters particularly for:

```text
Signal handling
Child-process cleanup
Container lifecycle
```

When Docker stops a container, the stop signal is delivered to the container's main process.

Therefore:

```text
Docker
   ↓
Signal
   ↓
PID 1
   ↓
Application shutdown behavior
```

If your startup design puts an unnecessary shell between Docker and the application, signal behavior may become less predictable.

---

# 34. Exec Form and PID 1

Consider:

```dockerfile
CMD ["python", "app.py"]
```

This is exec form.

The Python process can directly become the container's main process.

Conceptually:

```text
Container
└── PID 1: python app.py
```

Compare shell form:

```dockerfile
CMD python app.py
```

Conceptually, this can involve:

```text
Container
└── PID 1: /bin/sh
        └── python app.py
```

Now a shell exists between Docker and the application.

That can affect signal forwarding and process behavior.

Therefore, for long-running application processes:

> Prefer exec-form `CMD` or `ENTRYPOINT` unless you intentionally need shell behavior.

---

# 35. PID 1 and Child Processes

Some applications create child processes.

PID 1 also has responsibilities involving orphaned child processes.

If an application is not designed to behave correctly as PID 1, you may encounter zombie-process issues.

Docker supports:

```bash
docker run --init ...
```

which inserts a small init process.

Conceptually:

```text
Container
└── PID 1: tiny init
        └── application
```

The init process helps with signal forwarding and child-process reaping.

Do not add an init process automatically to every container without understanding the application.

---

# 36. Container Startup Commands

Your image needs a clear startup process.

Common options include:

```dockerfile
CMD ["python", "app.py"]
```

```dockerfile
CMD ["node", "server.js"]
```

or:

```dockerfile
ENTRYPOINT ["some-application"]
CMD ["default-argument"]
```

The startup command should normally:

```text
Start the actual application
Run in foreground
Return meaningful exit status
Handle signals correctly
Avoid unnecessary wrapper processes
```

---

# 37. Avoid Backgrounding the Main Application

Inside a container, you generally do not want:

```bash
my-server &
```

followed by a shell exiting.

Why?

Because the container's lifetime is tied to its main process.

If PID 1 exits:

```text
Main Process Exits
        ↓
Container Stops
```

The application should normally remain in the foreground.

# 40. Python Application

Create:

```text
app.py
```

with:

```python
import os
import signal
import sys

from flask import Flask, jsonify

app = Flask(__name__)

APP_NAME = os.getenv("APP_NAME", "VERIQTA Python API")
APP_ENV = os.getenv("APP_ENV", "development")
APP_VERSION = os.getenv("APP_VERSION", "1.0")


@app.get("/")
def home():
    return jsonify(
        application=APP_NAME,
        environment=APP_ENV,
        version=APP_VERSION,
        status="running",
    )


@app.get("/health")
def health():
    return jsonify(
        status="healthy",
        application=APP_NAME,
    ), 200


def shutdown_handler(signum, frame):
    print(
        f"Received signal {signum}. Shutting down.",
        flush=True,
    )
    sys.exit(0)


signal.signal(signal.SIGTERM, shutdown_handler)
signal.signal(signal.SIGINT, shutdown_handler)


if __name__ == "__main__":
    print(
        f"Starting {APP_NAME} in {APP_ENV}",
        flush=True,
    )

    app.run(
        host="0.0.0.0",
        port=5000,
    )
```

This application is deliberately simple so we can focus on container behavior.

# 46. Python Dockerfile

Create:

```text
Dockerfile
```

with:

```dockerfile
FROM python:3.12-slim

LABEL org.opencontainers.image.title="VERIQTA Python API"
LABEL org.opencontainers.image.description="Docker containerization training application"

ENV PYTHONDONTWRITEBYTECODE=1
ENV PYTHONUNBUFFERED=1
ENV APP_ENV=development
ENV APP_VERSION=1.0

WORKDIR /app

COPY requirements.txt .

RUN pip install --no-cache-dir -r requirements.txt

RUN useradd \
    --create-home \
    --shell /usr/sbin/nologin \
    appuser

COPY --chown=appuser:appuser app.py .

USER appuser

EXPOSE 5000

HEALTHCHECK \
    --interval=30s \
    --timeout=3s \
    --start-period=5s \
    --retries=3 \
    CMD ["python", "-c", "import urllib.request; urllib.request.urlopen('http://127.0.0.1:5000/health', timeout=2)"]

CMD ["python", "app.py"]
```

# 55. Important Production Note About Flask

The Flask development server is useful for this teaching lab.

It is not intended to be the production deployment server for a serious Flask application.

Production Python applications commonly use an application server such as:

```text
Gunicorn
uWSGI
Waitress
```

depending on the application/platform.

The important lesson is:

> Containerization does not magically turn a development server into a production server.

Docker packages and runs the application you give it.

---

# 56. Containerization Does Not Fix Application Architecture

If the application has:

```text
Bad security
Poor error handling
Broken shutdown behavior
Unsafe configuration
No health endpoint
Memory leaks
Bad database usage
```

Docker does not automatically solve those problems.

Think:

```text
Good Application Engineering
        +
Good Container Engineering
        =
Better Containerized Application
```

# 60. Why `package-lock.json` Matters

`package.json` describes dependency requirements.

`package-lock.json` records the resolved dependency tree much more precisely.

For reproducible container builds, you generally want the lockfile included.

This allows:

```bash
npm ci
```

to install according to the lockfile.

---

# 61. `npm install` vs `npm ci`

For application development:

```bash
npm install
```

is commonly used to install/update dependencies and can modify the lockfile.

For controlled CI/container builds with an existing lockfile:

```bash
npm ci
```

is often preferred.

It performs a clean dependency installation based on the lockfile and fails if the lockfile and package manifest are inconsistent.

That helps reproducibility.
