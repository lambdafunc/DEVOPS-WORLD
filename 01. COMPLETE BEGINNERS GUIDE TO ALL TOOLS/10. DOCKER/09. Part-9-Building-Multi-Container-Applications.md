# Part 9: Building Multi-Container Applications

Up to this point, you have mostly worked with individual containers.

You have learned how to:

- Run containers.
- Build Docker images.
- Write Dockerfiles.
- Containerize applications.
- Publish ports.
- Create Docker networks.
- Store persistent data using Docker volumes.
- Inspect containers.
- Read container logs.
- Troubleshoot basic networking and storage problems.

Now we are going to connect those skills.

Real applications are rarely one process running inside one container.

A typical application may contain:

- A frontend.
- A backend API.
- A database.
- A cache.
- A message queue.
- Background workers.
- Monitoring components.

Each component has a different responsibility.

Instead of putting everything inside one giant container, Docker allows us to run these components as separate containers and connect them together.

In this part, we will manually build this architecture:

                    USER'S BROWSER
                          |
                          |
                    Host Port 8080
                          |

                 +----------------+
                 |    Frontend    |
                 |   Container    |
                 +----------------+
                          |

                       HTTP/API
                          |
                          v
                 +----------------+
                 |    Backend     |
                 | API Container  |
                 +----------------+
                          |
                          |
                    PostgreSQL
                          |
                          v
                 +----------------+
                 |    Database    |
                 |   Container    |
                 +----------------+
                          |
                          |
                          v
                 +----------------+
                 | Docker Volume  |
                 | Persistent Data|
                 +----------------+

We will deliberately build this stack without Docker Compose.

That is important.

Docker Compose makes multi-container applications much easier, but you should first understand what Compose is automating.

By the end of this part, you should understand how several containers become one working application.

## 1. What We Are Building

We will build a small application containing three main services:

Frontend
Backend API
PostgreSQL Database

   |
   v
Backend API
   |

The frontend displays information to the user.

Docker will provide:

Containers

Volumes

Before building anything, we need to understand why applications are separated this way.

---

## 2. Why Applications Use Multiple Containers

Imagine that you are building an application with:

Nginx
Node.js
PostgreSQL

Technically, you could try installing all three inside one container.

The container might contain:

Ubuntu
├── Nginx
├── Node.js
├── Application
└── PostgreSQL

This may appear convenient at first.

But it creates several problems.

Suppose PostgreSQL needs upgrading.

Now you must rebuild the same container containing:

Nginx
Node.js
PostgreSQL
Application code

Suppose the backend needs three replicas but PostgreSQL should remain a single database.

You cannot scale them independently if everything is tightly bundled together.

Suppose PostgreSQL crashes.

Troubleshooting becomes more difficult because several unrelated processes are running inside the same container.

A better design is:

Frontend Container
        |
Backend Container
        |
Database Container

Each container has a clear responsibility.

---

## 3. One Concern Per Container

You will often hear this principle:

«One concern per container.»

This does not literally mean that a container can only run one operating-system process under every circumstance.

The more useful interpretation is:

«A container should normally have one clear application responsibility.»

For example:

frontend container
    responsibility: serve frontend content

backend container
    responsibility: execute application/API logic

database container
    responsibility: store and retrieve application data

This separation provides several advantages.

Independent deployment

You can update the backend without rebuilding the database.

Independent scaling

You might run:

Frontend: 2 containers
Backend: 5 containers
Database: 1 database service

Easier troubleshooting

If database requests fail, you can investigate the database separately.

Better security boundaries

The database does not need to be exposed directly to internet users.

Cleaner images

The frontend image does not need PostgreSQL installed.

The database image does not need Node.js installed.

Easier maintenance

Each service can use the software and runtime it actually requires.

## 7. The Database Container

The database stores persistent application data.

We will use PostgreSQL.

A database is fundamentally different from a stateless frontend container.

If you delete a frontend container, you can normally recreate it from its image.

But if you delete a database container and its data existed only inside the container's writable layer, you could lose important data.

That is why the database will use a Docker volume.

Our architecture becomes:

PostgreSQL Container
        |
        v
Docker Volume
        |
        v
Persistent Database Files

The container can be replaced while the data remains.

## 8. The Most Important Networking Question

When beginners first build multi-container applications, one question causes enormous confusion:

«How does one container find another container?»

Imagine:

Frontend Container
Backend Container
Database Container

These are separate environments.

The backend needs some address for PostgreSQL.

You might initially think:

localhost

But that is usually wrong.

---

## 9. Understanding localhost Inside Containers

"localhost" means:

«This machine or network namespace.»

Inside a container, "localhost" refers to that container itself.

Suppose the backend tries:

localhost:5432

The backend is effectively saying:

"Find PostgreSQL inside my own container on port 5432."

But PostgreSQL is running in another container.

Therefore:

Backend container
localhost:5432
       X
Database container

The connection fails.

This is one of the most common Docker networking mistakes.

Instead, containers should communicate through a Docker network.

---

## 10. Docker Networks

Docker networks allow containers to communicate.

We will create a user-defined bridge network.

The command is:

docker network create app-network

Let's break this down.

"docker"

Runs the Docker CLI.

"network"

Tells Docker we want to work with Docker networks.

"create"

Creates a new network.

"app-network"

The name we are assigning to the network.

Verify it:

docker network ls

Example output:

NETWORK ID     NAME          DRIVER    SCOPE
abc123         bridge        bridge    local
def456         host          host      local
ghi789         none          null      local
xyz987         app-network   bridge    local

Our application will use:

app-network

Inspect it:

docker network inspect app-network

At first, the container list may be empty because we have not attached containers yet.

---

## 11. User-Defined Bridge Networks

Docker provides a default bridge network, but user-defined bridge networks are generally preferable for application stacks.

Our network will look like:

                app-network

     +-----------------------------+
     |                             |
     |    Frontend Container       |
     |                             |
     |    Backend Container        |
     |                             |
     |    PostgreSQL Container     |
     |                             |
     +-----------------------------+

Containers connected to the same user-defined network can communicate with each other.

More importantly, Docker provides DNS-based name resolution.

---

## 12. Docker DNS

DNS stands for:

Domain Name System

Normally, DNS translates names such as:

example.com

into IP addresses.

Docker provides similar name resolution for containers on user-defined networks.

Suppose our containers are named:

frontend
backend
database

Docker allows the backend to contact:

database

instead of needing to know an IP address.

Conceptually:

Backend asks:

"Where is database?"

        |
        v

Docker DNS

        |
        v

Database container IP

        |
        v

Connection established

This matters because container IP addresses can change.

Hardcoding container IP addresses is therefore a poor design.

Bad:

DB_HOST=172.18.0.4

Better:

DB_HOST=database

Docker DNS resolves "database" to the appropriate container.

---

## 13. Container Names Become Useful Network Names

If we create a container like this:

docker run --name database ...

and connect it to:

app-network

another container on the same network can usually reach it using:

database

For PostgreSQL:

database:5432

For a backend running on port 3000:

backend:3000

This is the foundation of service-to-service communication in our manual stack.

---

## 14. External Ports vs Internal Communication

This distinction is critical.

Suppose PostgreSQL listens on:

5432

Does the host need access to it?

Maybe.

Does the internet need access to it?

Usually not.

Containers on the same Docker network can communicate without publishing the database port to the host.

For example:

Backend
   |
   | database:5432
   v
PostgreSQL

No host port is required for that communication.

This means the database can remain internal.

---

## 15. Published Ports

When you write:

-p 8080:80

you are publishing a container port to the host.

The structure is:

-p HOST_PORT:CONTAINER_PORT

So:

-p 8080:80

means:

Host port 8080
       |
       v
Container port 80

A browser might therefore access:

http://localhost:8080

Docker forwards that traffic to port "80" inside the container.

---

## 16. Internal-Only Services

Not every service should be exposed to the host.

Consider:

Internet
   |
   v
Frontend
   |
   v
Backend
   |
   v
Database

Depending on the architecture, only the frontend might require an externally published port.

The database can remain internal.

This reduces unnecessary exposure.

For example, this database command:

docker run \
  --name database \
  --network app-network \
  postgres:16

does not contain:

-p 5432:5432

Therefore PostgreSQL is not published through a host port.

The backend can still communicate with it over "app-network".

## 21. Start the PostgreSQL Container

Run:

docker run -d \
  --name database \
  --network app-network \
  -e POSTGRES_USER=appuser \
  -e POSTGRES_PASSWORD=devpassword \
  -e POSTGRES_DB=appdb \
  -v postgres-data:/var/lib/postgresql/data \
  postgres:16

Do not blindly copy commands like this without understanding them.

Let's examine every important part.

"docker run"

Creates and starts a container from an image.

"-d"

Means:

detached mode

The container runs in the background.

"--name database"

Names the container:

database

This name is useful for both administration and Docker DNS.

"--network app-network"

Connects the container to:

app-network

"-e"

Sets an environment variable.

We define:

POSTGRES_USER=appuser
POSTGRES_PASSWORD=devpassword
POSTGRES_DB=appdb

The PostgreSQL image reads these during initialization.

"-v"

Mounts storage.

postgres-data:/var/lib/postgresql/data

means:

Docker volume
postgres-data

        mounted at

/var/lib/postgresql/data
inside the container

PostgreSQL stores its database files there.

"postgres:16"

The image used to create the container.

For this local lab, "devpassword" is intentionally simple. Do not copy this secret-management pattern into production.

## 25. Create the Backend Code

Create:

server.js

Add:

const express = require("express");
const { Pool } = require("pg");

const app = express();
const port = process.env.PORT || 3000;

const pool = new Pool({
  host: process.env.DB_HOST,
  port: process.env.DB_PORT || 5432,
  user: process.env.DB_USER,
  password: process.env.DB_PASSWORD,
  database: process.env.DB_NAME
});

app.get("/health", async (req, res) => {
  try {
    await pool.query("SELECT 1");
    res.status(200).json({
      status: "healthy",
      database: "connected"
    });
  } catch (error) {
    res.status(503).json({
      status: "unhealthy",
      database: "disconnected"
    });
  }
});

app.get("/api/message", async (req, res) => {
  try {
    const result = await pool.query(
      "SELECT 'Hello from PostgreSQL through the backend API!' AS message"
    );

    res.json({
      message: result.rows[0].message
    });
  } catch (error) {
    console.error("Database query failed:", error.message);

    res.status(500).json({
      error: "Database query failed"
    });
  }
});

app.listen(port, "0.0.0.0", () => {
  console.log(`Backend listening on port ${port}`);
});

Let's understand the important architecture.

## 26. Backend Database Configuration

The backend reads:

process.env.DB_HOST
process.env.DB_PORT
process.env.DB_USER
process.env.DB_PASSWORD
process.env.DB_NAME

These values are not permanently hardcoded into the application.

Instead, they will be injected when the container starts.

This separates:

Application code

from:

Environment-specific configuration

That is an important container design pattern.

---

## 27. Why Environment Variables Matter

Imagine the same backend running in:

Development
Testing
Staging
Production

The database host will probably differ.

Hardcoding:

host: "database"

might work locally but makes the application less portable.

Instead:

host: process.env.DB_HOST

allows the environment to decide the value.

Locally:

DB_HOST=database

Staging might use another database endpoint.

Production might use a managed database hostname.

The code does not have to change.

---

## 28. Database Connection Strings

Applications often represent database configuration as individual variables:

DB_HOST
DB_PORT
DB_USER
DB_PASSWORD
DB_NAME

or as one connection string.

For PostgreSQL, a connection string can look like:

postgresql://appuser:password@database:5432/appdb

Break it down:

postgresql://

Protocol/database type.

appuser

Username.

password

Password.

database

Hostname.

5432

PostgreSQL port.

appdb

Database name.

Do not commit real production credentials into Git.

Connection strings often contain secrets.

## 33. Verify Docker DNS Directly

A useful debugging technique is to test name resolution from another container attached to the same network.

Run:

docker run --rm \
  --network app-network \
  busybox \
  nslookup database

"--rm" means Docker automatically removes this temporary container after it exits.

"--network app-network" places it on the same network.

"busybox" is a small utility image.

"nslookup database" asks DNS to resolve the name "database".

You should see an address associated with the database container.

The exact IP may differ.

That is precisely why we use names instead of hardcoded IP addresses.

      .then(response => {
        if (!response.ok) {

        }

        return response.json();
      })
      .then(data => {
        document.getElementById("status").textContent = data.message;
      })
      .catch(error => {
        document.getElementById("status").textContent =

      });
  </script>
</body>

Notice something important.

The browser calls:

/api/message

It does not call:

http://backend:3000/api/message

Why?

Because Docker DNS names such as "backend" exist inside the Docker network.

Your web browser is running outside that Docker network.

We therefore need the frontend web server to proxy "/api/" requests to the backend.

This is an important real-world networking distinction.

---

## 36. Browser Networking Is Not Container Networking

Consider this:

Browser
   |
   X
backend:3000

Your browser generally does not know what Docker's internal "backend" hostname means.

But the frontend container does.

Therefore we can use Nginx as a reverse proxy:

Browser
   |
   | /api/message
   v
Frontend/Nginx
   |
   | backend:3000
   v
Backend

This also keeps the browser-facing architecture cleaner.

---

## 37. Create the Nginx Configuration

Create:

nginx.conf

Add:

server {
    listen 80;

    location / {
        root /usr/share/nginx/html;
        index index.html;
    }

    location /api/ {
        proxy_pass http://backend:3000;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
}

The important line is:

proxy_pass http://backend:3000;

Nginx runs inside the frontend container.

The frontend container is connected to:

app-network

Therefore Docker DNS can resolve:

backend

   |
   v
Browser

If you understand that path, you understand one of the most important ideas in containerized application architecture.

## 44. Why the Database Has No Published Port

Run:

docker ps

Look at the "PORTS" column.

The frontend might show:

0.0.0.0:8080->80/tcp

The backend might show:

0.0.0.0:3000->3000/tcp

PostgreSQL should not show a host mapping such as:

0.0.0.0:5432->5432/tcp

because we did not publish it.

Yet the backend still reaches:

database:5432

This demonstrates the difference between:

Container-to-container networking

and:

Host-to-container port publishing

They are not the same thing.

## 45. Can We Hide the Backend Too?

Yes.

We published:

-p 3000:3000

on the backend because it makes learning and debugging easier.

But the browser-facing application does not actually require that mapping.

The frontend communicates with the backend through:

app-network

Therefore we could recreate the backend without publishing port 3000.

First remove it:

docker rm -f backend

Warning:

"-f" forcibly stops and removes the container.

Use it only when you understand which container you are targeting.

Recreate it:

docker run -d \
  --name backend \
  --network app-network \
  -e DB_HOST=database \
  -e DB_PORT=5432 \
  -e DB_USER=appuser \
  -e DB_PASSWORD=devpassword \
  -e DB_NAME=appdb \
  multi-backend:1.0

Now:

Internet/Host
      |
      v
Frontend
      |
      v
Backend
      |
      v
Database

Only the frontend needs a host-facing published port.

That is a cleaner architecture for this lab.

## 46. Internal and External Boundaries

We can now classify services.

Externally reachable

Frontend:

Internal-only

Backend:

Database:

This principle becomes extremely important in production.

Do not expose a service simply because you can.

Expose only what actually needs to receive traffic from outside its trusted network boundary.

## 48. Environment Variables Are Not a Secret Vault

Environment variables are useful for configuration.

But do not assume that placing a password in an environment variable automatically makes it secure.

For example:

docker inspect backend

may reveal environment configuration to users with sufficient Docker access.

For a beginner local lab, using:

DB_PASSWORD=devpassword

is acceptable.

For production systems, secrets require stronger handling.

Later production architectures may use:

- Docker secrets in appropriate environments.
- Cloud secret managers.
- AWS Secrets Manager.
- HashiCorp Vault.
- Kubernetes Secrets combined with appropriate security controls.
- CI/CD secret stores.

The important lesson is:

«Configuration and secret management are related, but they are not identical.»

## 49. Startup Dependencies

Our backend depends on PostgreSQL.

The frontend depends on the backend.

So logically:

Database
   |
   v
Backend
   |
   v
Frontend

You might think we should simply start them in this order.

That helps, but it does not completely solve the problem.

## 50. Started Does Not Mean Ready

Imagine PostgreSQL starts at:

10:00:00

The container process exists immediately.

But PostgreSQL may require several seconds to initialize.

The backend starts at:

10:00:01

and immediately attempts a connection.

PostgreSQL may still be initializing.

The connection fails.

This teaches an important principle:

Container running

does not necessarily mean:

Application ready

---

## 51. Startup Order Is Not Readiness

These are different questions.

Startup order asks:

«Which container was launched first?»

Readiness asks:

«Is the application inside that container ready to serve requests?»

For example:

docker ps

might show:

database   Up 2 seconds

But PostgreSQL could still be initializing.

Applications should therefore be designed to tolerate temporary dependency failures.

Typical techniques include:

- Connection retries.
- Backoff.
- Health checks.
- Readiness checks.
- Graceful error handling.

Docker Compose will later help coordinate dependencies, but even Compose cannot replace good application-level resilience.

## 52. Health Checks

A health check asks:

«Is this application actually functioning?»

That is more useful than merely checking whether the process exists.

For PostgreSQL, a useful health command is:

pg_isready

You can test it manually:

docker exec database pg_isready -U appuser -d appdb

Expected result resembles:

/var/run/postgresql:5432 - accepting connections

That tells us PostgreSQL is ready.

## 53. Backend Health Endpoint

We already created:

/health

Our backend performs:

SELECT 1

against PostgreSQL.

Therefore the endpoint checks more than:

"Is Node.js running?"

It also verifies database connectivity.

Request:

GET /health

Healthy:

{
  "status": "healthy",
  "database": "connected"
}

Database unavailable:

{
  "status": "unhealthy",
  "database": "disconnected"
}

That is much more useful operationally.

## 54. Docker-Level Health Checks

Containers can also have Docker health checks.

For example, a PostgreSQL container could be created with:

docker run -d \
  --name database \
  --network app-network \
  -e POSTGRES_USER=appuser \
  -e POSTGRES_PASSWORD=devpassword \
  -e POSTGRES_DB=appdb \
  -v postgres-data:/var/lib/postgresql/data \
  --health-cmd="pg_isready -U appuser -d appdb" \
  --health-interval=10s \
  --health-timeout=5s \
  --health-retries=5 \
  postgres:16

Important options:

--health-cmd

defines the command Docker runs.

--health-interval=10s

runs the check every ten seconds.

--health-timeout=5s

allows each check five seconds before considering it failed.

--health-retries=5

requires repeated failures before Docker marks the container unhealthy.

Inspect status:

docker ps

You may see:

healthy

or:

unhealthy

Inspect detailed health information:

docker inspect database

## 55. Persistent Database Storage

Let's prove that our volume matters.

First connect to PostgreSQL:

docker exec -it database psql -U appuser -d appdb

Create a table:

CREATE TABLE notes (
    id SERIAL PRIMARY KEY,
    message TEXT NOT NULL
);

Insert data:

INSERT INTO notes (message)
VALUES ('Docker volumes keep database data persistent.');

Read it:

SELECT * FROM notes;

You should see the row.

Exit:

\q

Now remove the database container.

Warning: verify the container name before deleting it.

docker rm -f database

The container is gone.

Check:

docker ps -a

But the volume still exists:

docker volume ls

You should still see:

postgres-data

## 56. Recreate the Database

Run:

docker run -d \
  --name database \
  --network app-network \
  -e POSTGRES_USER=appuser \
  -e POSTGRES_PASSWORD=devpassword \
  -e POSTGRES_DB=appdb \
  -v postgres-data:/var/lib/postgresql/data \
  postgres:16

Wait until PostgreSQL is ready.

Then:

docker exec -it database psql -U appuser -d appdb

Run:

The row should still exist.

Why?

Because:

Container lifecycle

and:

Volume lifecycle

are separate.

The container was destroyed.

The volume remained.

This is one of the most important ideas when containerizing stateful applications.

## 62. Failure Scenario 1: Database Stops

Stop PostgreSQL:

docker stop database

Now request:

http://localhost:8080

The page may load because Nginx still works.

But the API request should fail because:

Frontend
   |
   v
Backend
   |
   X
Database stopped

Check backend health if its port is temporarily published, or test from inside the Docker network.

Check backend logs:

docker logs backend

Check database state:

docker ps -a

You should see the database stopped.

Fix:

docker start database

Verify:

docker ps

Then test again.

This demonstrates an important concept:

«A multi-container application can be partially available.»

The frontend can be running while the overall application is unhealthy.

---

## 63. Failure Scenario 2: Wrong Database Hostname

Suppose the backend is configured with:

DB_HOST=postgres

but the actual container name is:

database

Docker DNS cannot resolve the expected service name.

You might see an error similar to:

getaddrinfo ENOTFOUND postgres

This is a DNS/name-resolution problem.

Investigate:

docker network inspect app-network

Check which containers are connected.

Then inspect the backend configuration:

docker inspect backend

Look for:

DB_HOST

Correct it by recreating the container with:

DB_HOST=database

---

## 64. Failure Scenario 3: Containers on Different Networks

Suppose:

backend → app-network
database → another-network

Even if both containers are running, they may not be able to communicate through the expected Docker network.

Check:

docker network inspect app-network

If "database" is missing, connect it:

docker network connect app-network database

Verify again:

docker network inspect app-network

The database should now appear.

This is why:

running

does not automatically mean:

reachable

---

## 65. Failure Scenario 4: Wrong Port

Suppose the backend tries:

database:3306

But PostgreSQL listens on:

5432

The hostname may resolve correctly, but the application still cannot connect.

This is not primarily a DNS problem.

It is a port/service mismatch.

Check the backend configuration:

DB_PORT

Correct value:

5432

This demonstrates why troubleshooting should distinguish:

Name resolution
Network reachability
Port availability
Application readiness
Authentication

These are different layers of failure.

---

## 66. Failure Scenario 5: Wrong Database Credentials

Suppose:

DB_USER=wronguser

or the password is incorrect.

The backend reaches PostgreSQL, but authentication fails.

This is a different class of failure.

The network works.

DNS works.

PostgreSQL is listening.

But credentials are invalid.

Check:

docker logs backend

and:

docker logs database

You may find authentication-related messages.

The troubleshooting lesson is:

«A failed connection does not automatically mean the network is broken.»

---

## 67. Failure Scenario 6: Frontend Cannot Reach Backend

Suppose the frontend Nginx configuration contains:

proxy_pass http://api:3000;

but the backend is named:

backend

Nginx may report that it cannot resolve the upstream host.

Inspect:

docker logs frontend

Check:

docker network inspect app-network

Confirm the actual backend name.

Correct:

proxy_pass http://backend:3000;

Then rebuild the image:

docker build -t multi-frontend:1.1 .

Remove the old container:

docker rm -f frontend

Start the new version:

docker run -d \
  --name frontend \
  --network app-network \
  -p 8080:80 \
  multi-frontend:1.1

Verify in the browser.

---

## 68. Failure Scenario 7: Port Already in Use

Suppose another program already uses port "8080".

This command:

docker run -p 8080:80 ...

may fail because Docker cannot bind the host port.

Investigate which service is using the port.

On Linux, one option is:

ss -ltnp

You can narrow it:

ss -ltnp | grep :8080

Then either stop the conflicting service if appropriate or choose another host port:

-p 8081:80

Now access:

http://localhost:8081

Remember:

8081 = host port
80   = container port

Changing the host port does not require Nginx inside the container to stop listening on port 80.

---

## 69. Failure Scenario 8: Database Container Deleted

Suppose someone runs:

docker rm -f database

The application breaks.

But if the database uses:

postgres-data

we can recreate the container and attach the same volume.

The data survives.

Without persistent storage, deleting the database container could destroy data stored only in the container writable layer.

That is why persistent storage is an architectural requirement for stateful services.

---

## 70. Failure Scenario 9: Volume Deleted

Be careful.

Deleting the container and deleting the volume are very different operations.

This removes a container:

docker rm database

This removes a volume:

docker volume rm postgres-data

If important database files exist only in that volume, deleting the volume can destroy the persistent data.

Do not blindly run volume deletion or aggressive prune commands on systems containing important data.

Before deleting storage, understand:

What uses it?
What data exists there?
Is it backed up?
Can it be recreated?

---

## 71. Failure Scenario 10: Backend Starts Before Database Is Ready

You may see intermittent startup failures.

Sequence:

Docker starts database
        |
        v
Database process initializing

Docker starts backend
        |
        v
Backend immediately connects
        |
        X
Database not ready yet

A fragile application crashes permanently.

A better application may retry.

Conceptually:

Attempt connection
       |
       X
Wait
       |
Retry
       |
       X
Wait longer
       |
Retry
       |
       ✓
Continue startup

This introduces the concept of retry and backoff.

Production applications should not assume every dependency is instantly available.

## 78. Common Beginner Mistakes

Mistake 1: Using localhost between containers

Wrong:

DB_HOST=localhost

when PostgreSQL is in another container.

Correct:

DB_HOST=database

on the shared Docker network.

---

Mistake 2: Publishing every port

Beginners sometimes expose:

Frontend
Backend
Database
Redis
Everything

to the host.

Do not publish a port unless something outside the Docker network needs to reach it.

---

Mistake 3: Hardcoding container IP addresses

Avoid:

172.18.0.3

Prefer:

database

Container IPs may change.

Docker DNS gives you stable service naming.

---

Mistake 4: Storing database data only inside the container

If the container is removed, data may disappear.

Use persistent storage.

---

Mistake 5: Assuming running means healthy

A container can be:

Up

while the application inside it is broken.

Use logs, health checks, and functional requests.

---

Mistake 6: Treating environment variables as perfect secret storage

They are useful configuration mechanisms, but production secret management requires additional controls.

---

Mistake 7: Restarting everything before investigating

Restarting may temporarily hide the problem and destroy useful evidence.

Inspect first.

---

Mistake 8: Troubleshooting the wrong layer

If PostgreSQL authentication fails, rebuilding the frontend probably will not help.

Follow the dependency path.
