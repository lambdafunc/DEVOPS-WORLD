## Welcome to DevOps Interview World

DevOps interviews are rarely about memorizing definitions.

You may be asked to troubleshoot a Linux server, diagnose a networking problem, repair a broken CI/CD pipeline, debug a container, investigate a Kubernetes failure, review Terraform, trace a production incident, analyze monitoring data, or explain why you chose one architecture over another.

**DevOps Interview World** is a hands-on interview preparation repository built around those situations.

It is designed for engineers preparing for:

* DevOps Engineer
* Site Reliability Engineer
* Platform Engineer
* Cloud Engineer
* Infrastructure Engineer
* DevSecOps Engineer
* Production Engineer

The repository combines interview questions with practical engineering work so you can practice not only **what to answer**, but also **how to investigate, troubleshoot, verify, and explain your decisions**.

# What You Will Find Here

This repository is built around practical interview preparation.

Each section can contain:

* hands-on interview questions
* terminal exercises
* troubleshooting challenges
* production scenarios
* broken configurations
* debugging exercises
* architecture questions
* CI/CD failures
* Kubernetes incidents
* cloud troubleshooting
* observability investigations
* security scenarios
* SRE exercises
* step-by-step solutions
* expected outputs
* verification steps
* engineering explanations
* follow-up interview questions

The objective is not to memorize a list of commands.

The objective is to develop the reasoning needed to investigate unfamiliar systems under interview and production conditions.

# Interview Tracks

| Role                        | Recommended Path                                                                         |
| --------------------------- | ---------------------------------------------------------------------------------------- |
| **DevOps Engineer**         | Linux → Networking → Git → Containers → CI/CD → Kubernetes → IaC → Cloud → Observability |
| **SRE**                     | Linux → Networking → Kubernetes → Observability → Reliability → Incident Response        |
| **Platform Engineer**       | Containers → Kubernetes → IaC → GitOps → Cloud → Observability → Security                |
| **Cloud Engineer**          | Linux → Networking → AWS/Azure/GCP → IaC → IAM → Containers                              |
| **Infrastructure Engineer** | Linux → Networking → Terraform → Ansible → Cloud                                         |
| **DevSecOps Engineer**      | Git → CI/CD → Containers → Kubernetes → IAM → Secrets → Security                         |
| **Junior DevOps Engineer**  | Foundations → Guided Questions → Hands-On Labs                                           |
| **Senior DevOps Engineer**  | Troubleshooting → Production Incidents → Architecture → Reliability                      |

# Difficulty Levels

| Level            | Focus                                                                                   |
| ---------------- | --------------------------------------------------------------------------------------- |
| 🟢 **Junior**    | Fundamentals, common commands, basic configuration and guided troubleshooting           |
| 🟡 **Mid-Level** | Failure diagnosis, production troubleshooting and engineering decisions                 |
| 🔴 **Senior**    | Ambiguous incidents, architecture, reliability, trade-offs and complex failure analysis |

Difficulty reflects the reasoning required to solve the problem, not simply the number of commands involved.

# How to Solve an Interview Challenge

## 1. Read the scenario

Understand what is actually failing.

Do not immediately start running commands.

## 2. Separate facts from assumptions

Identify what the scenario proves and what you are only assuming.

## 3. Build hypotheses

List the most plausible causes.

## 4. Investigate

Choose commands, logs, metrics, traces, configuration files, or APIs that can prove or disprove each hypothesis.

## 5. Identify the root cause

Do not stop at the first suspicious symptom.

## 6. Apply the fix

Use the smallest appropriate change that addresses the root cause.

## 7. Verify

Prove that the system has recovered.

## 8. Explain your reasoning

Be prepared to explain:

* what failed
* what evidence you collected
* how you narrowed the problem
* what the root cause was
* why your solution works
* what risks the solution introduces
* how you would prevent recurrence

That final step matters.

Finding the command is useful.

Explaining **why that command is appropriate** demonstrates engineering understanding.

---

# Do Not Memorize Commands

Running:

```bash
kubectl get pods
```

is not the skill being tested.

The important questions are:

**Why are you checking the Pods?**

**What evidence are you looking for?**

**What will you investigate next if the Pods are healthy?**

The same principle applies across Linux, networking, Git, containers, Kubernetes, Terraform, CI/CD, cloud platforms, security and observability.

This repository is built around that mindset.

# Think Like a Production Engineer

Many exercises intentionally go beyond:

> What command fixes this?

You may also need to answer:

> Why did this happen?

> What evidence confirms the root cause?

> How would you verify the fix?

> Could your fix create another failure?

> How would you detect this earlier?

> What should be monitored?

> What could be automated?

> How would you prevent recurrence?

> What belongs in the postmortem?

Those are the questions that turn troubleshooting into engineering.

# Repository Principles

DevOps Interview World is built around a few simple principles.

**Hands-on over memorization.**

You should be able to use the technology, not simply define it.

**Evidence over guessing.**

Troubleshooting should be driven by observable evidence.

**Root cause over symptoms.**

Fixing a symptom without understanding the failure is incomplete.

**Verification over assumption.**

A change is not complete until you prove it worked.

**Production thinking over toy examples.**

Exercises should help you reason about systems that resemble real engineering environments.

**Explanation over command recall.**

Strong engineers can explain why they made a decision.
